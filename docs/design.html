설계

"에이전트를 만들었다"가 아니라 "평가로 인용 정확도를 얼마나 올렸다"는 숫자를 남기는 것이 목표입니다. 그래서 평가셋과 baseline을 먼저 만들고, 기능은 하루에 하나씩 더하며 숫자로 효과를 확인합니다.

평가 설계

평가가 이 프로젝트의 본체입니다. 같은 평가셋, 같은 지표로 네 변형을 비교하고 그 결과표가 README와 LinkedIn 글의 헤드라인이 됩니다.

평가셋

셋규모구성재는 것
PubMedQA 서브셋100문항전문가 라벨 셋(PQA-L)에서 무작위 추출, 문항마다 원 논문 PMID 존재정답률, 원 논문 검색 성공률
도메인 셋25문항MSI · dPCR · liquid biopsy 질문 직접 작성, 문항마다 꼭 인용할 PMID와 핵심 포인트 2–4개핵심 포인트 커버리지, must-cite recall
판정 보정셋60쌍에이전트 출력의 (문장, 인용 초록) 쌍을 직접 라벨링LLM judge와 사람 판정의 일치도
범위 밖 질문10문항개인 치료 결정 요청 등연구 탐색 범위로 안내하는지

비교 변형

변형구성보여주는 것
A. LLM 단독도구 없이 답변 + PMID 인용 요청인용 환각이 실제로 얼마나 일어나는가
B. 단순 RAG질문 그대로 PubMed 상위 10건 초록 → 답변일반적인 RAG의 한계
C. 에이전트질문 분해, MeSH 검색어, 초록 선별, 재검색 1회. 상세 설계에이전트 설계의 효과
D. 에이전트 + 검증C + 인용 판정, 인용 정리, 고쳐 쓰기 1회, 삭제. 상세 설계검증 루프의 효과와 그 비용

PubMedQA 질문은 논문 제목에서 만들어져 검색 성공률이 낙관적으로 나오고, 모델이 학습 중 봤을 가능성도 있습니다. 그래서 직접 만든 도메인 셋 결과를 항상 함께 제시합니다.

평가 하네스

평가 하네스는 "문항 × 변형"마다 답변을 하나 받아, 사람 손을 거치지 않는 결정적 지표부터 채점합니다. 판정이 필요한 지표(citation precision, coverage)는 judge가 같은 레코드 위에 더합니다. 그래서 레코드는 나중에 다시 실행하지 않고 재채점할 수 있게 원자료를 모두 남깁니다.

리서치 에이전트 구현됨

변형 C는 B와 같은 답변 단계에 "무엇을 읽을지 고르는 일"만 더합니다. 질문을 개념으로 나눠 검색어를 쓰고, 찾은 초록을 읽어 근거가 되는 논문만 고르고, 부족하면 한 번 더 찾습니다. 답변 단계의 시스템 프롬프트, 출력 스키마, 초록 수 상한(10건)은 B와 같습니다. 그래서 B와 C의 차이는 "어떤 초록을 읽었나"에서만 나옵니다.

설계 결정

결정이유버린 대안
답변 단계는 B와 같은 시스템 프롬프트, 스키마, 초록 상한 10건B 대비 개선이 검색·선별에서 왔다고 말할 수 있음. 공유 프롬프트는 src/bioscout/prompts.py로 옮겨 두 변형이 같은 상수를 씀에이전트 전용 답변 프롬프트

인용 판정 judge 구현됨

judge는 답변의 문장 하나와 그 문장이 인용한 초록들을 받아, 초록이 문장을 뒷받침하는지 판정합니다. 평가에서는 이 판정으로 citation precision과 coverage를 계산합니다. 변형 D에서는 같은 judge가 답변을 보여 주기 전에 문장을 걸러 냅니다.

흐름

  1. 답변이 인용한 PMID의 초록을 PubMed에서 가져옵니다(캐시).
  2. PubMed에 없는 PMID와 초록이 없는 논문은 LLM을 부르지 않고 unsupported로 둡니다.
  3. 판정할 초록이 하나라도 있으면 문장마다 LLM을 한 번 부릅니다. 질문, 문장, 인용한 초록들을 주고 인용별 판정과 근거 구절, 문장 판정, 뒷받침되지 않은 부분을 받습니다.
  4. 일관성 규칙을 코드로 적용합니다. 문장 판정은 가장 좋은 인용 판정보다 높을 수 없고, supported 인용이 있으면 문장은 partial 이상입니다. judge가 빠뜨린 PMID는 unsupported로 두고, 주지 않은 PMID에 대한 판정은 버립니다.
  5. 결과를 evals/runs/<run_id>/judgments.jsonl에 문장 단위로 저장합니다. 답변 레코드는 바꾸지 않습니다.

추출judge가 LLM으로 판정한 인용을 판정별(supported, partial, unsupported)로 나누고, 판정마다 같은 수를 뽑음. 한 판정이 모자라면 남는 몫을 다른 판정에 넘김. 각 판정 안에서는 변형 A, B, C에서 번갈아 뽑음전체 인용의 86%가 supported라 무작위로 뽑으면 60쌍 중 unsupported가 1쌍도 안 나옴. 그러면 judge가 틀린 인용을 잡는지는 확인할 수 없음

고쳐 쓰기는 한 번, 답변당 호출 한 번비용 상한이 분명함. 한 번 고쳐도 부분 지지면 표시하고 넘어감지지가 될 때까지 반복
부분 지지 문장은 지우지 않고 표시주제가 맞는 근거가 있고, 읽는 사람이 판단할 수 있음. 지우면 답변이 빈약해짐부분 지지도 삭제

삭제한 문장을 이유와 함께 기록무엇이 빠졌는지 추적할 수 있고, 평가에서 답변당 삭제 문장 수를 집계함조용히 삭제

D의 수치를 읽는 법

D는 judge로 거른 답변입니다. 그 답변을 같은 judge로 다시 채점하면 precision은 구조적으로 높게 나옵니다. 그래서 D의 citation precision은 "judge가 supported라고 한 인용을 사람도 그렇게 보는 비율"만큼만 믿을 수 있고, 이 비율은 보정 표본에서 나옵니다. D의 결과는 보정 결과, 답변당 삭제한 문장 수, coverage, 비용과 함께 봅니다.

결정이유버린 대안
OpenTelemetry로 내보내고 Langfuse는 받는 쪽으로 둠Langfuse가 OTLP를 그대로 받음. 다른 OTLP 백엔드로도 보낼 수 있고, 테스트는 메모리 내보내기로 네트워크 없이 span을 확인함Langfuse SDK를 코드 곳곳에서 직접 호출
속성 이름은 Langfuse의 OpenTelemetry 매핑을 따름(langfuse.observation.*)모델 호출이 generation으로 잡혀 토큰과 비용이 Langfuse 화면에 집계됨임의의 속성 이름
설정이 없으면 완전히 꺼짐키가 없으면 LLM과 PubMed 객체를 감싸지 않고 그대로 씀. 기존 실행, 캐시, 평가 수치에 영향이 없음항상 span을 만들고 내보내기만 끔
모델과 PubMed 호출은 감싸는 객체로 기록에이전트가 쓰는 인터페이스(LLM, Literature)를 감싸므로 변형 A–D와 judge가 모두 같은 방식으로 기록되고, 가짜 LLM으로 테스트할 수 있음Claude 클라이언트 안에서 기록
캐시에서 재생한 응답은 비용을 0으로 보냄지금 쓴 돈이 아님. 처음 만들 때의 비용은 메타데이터에 따로 남김재생도 원래 비용으로 집계
내용을 빼고 보낼 수 있음(BIOSCOUT_TRACE_CONTENT=off)질문, 프롬프트, 응답 없이 이름, 횟수, 토큰, 비용만 보냄. 외부 서비스에 내용을 두고 싶지 않을 때 씀항상 전체 내용 전송
초록 본문은 PubMed span에 넣지 않음그 초록을 읽는 모델 호출의 프롬프트에 이미 들어 있음. 같은 본문을 두 번 보내지 않음도구 결과 전체를 기록

OpenTelemetry 패키지는 선택 설치(trace)MCP 서버나 평가만 쓰는 설치를 가볍게 유지. 패키지가 없으면 트레이싱 테스트는 건너뜀기본 의존성에 추가

확인한 것과 남은 것

가짜 LLM과 가짜 PubMed로 에이전트를 돌려 span의 부모 관계, 종류, 토큰과 비용, 세션과 태그를 테스트합니다. 실제 데이터로는 예시 질문 하나를 캐시에서 재생하면서, Langfuse 자리에 로컬 수신기를 세워 전송을 확인했습니다. 요청은 /api/public/otel/v1/traces로 한 번 갔고, 인증 헤더가 맞았고, span 19개가 한 trace로 도착했습니다. 검증 단계의 judge 호출 5개는 동시에 실행돼도 verify 아래에 달렸습니다. 새로 든 비용은 없습니다.

이 확인 과정에서 데모 경로의 버그 하나를 찾아 고쳤습니다. 단위 테스트가 지나가지 않던 줄이어서, 그 줄을 지나는 테스트를 더했습니다.

실제 Langfuse 화면에서는 아직 보지 못했습니다. Langfuse 계정의 키가 없기 때문입니다. 키를 넣고 scripts/trace_check.py를 실행해 화면에 trace가 보이면 끝납니다.

공개 배포 (Hugging Face Space)

결정이유버린 대안
공개 주소는 Static Space에 올린 정적 페이지 한 장Hugging Face가 Docker Space 호스팅에 유료 플랜을 요구함. Docker Space 생성 요청이 402로 거절됐음. Static Space는 무료이고 잠들지 않아 링크를 누르면 바로 열림유료 플랜으로 Docker Space 운영. 다른 호스팅에 새 계정 만들기
정적 페이지는 Streamlit 화면과 같은 기록 파일(app/examples.json)을 읽음답변을 HTML에 옮겨 적지 않으므로 두 화면의 내용이 어긋나지 않음. 판정, 삭제 이유, 단계 이름의 문구가 Streamlit 화면과 같은지는 테스트가 확인답변을 HTML에 직접 써넣기
공개 페이지에서는 모델을 부르지 않음세션당 질문 한도는 새로 고치면 풀리므로, 공개 주소에 API 키를 두면 비용에 상한이 없음. 전체 질문 수 한도를 만들기 전까지는 기록된 답변만 보여 줌키를 넣고 세션 한도만으로 공개
올릴 파일은 스크립트가 목록으로 골라 임시 폴더에 모은 뒤 한 번에 올림저장소 전체를 올리지 않으므로 .env, 캐시, 평가 기록이 섞일 수 없음. 올라가는 파일 목록은 테스트가 확인저장소를 Space에 그대로 push
배포는 PC에 저장된 Hugging Face 로그인으로 실행토큰을 저장소나 CI 비밀값에 두지 않음GitHub Actions가 토큰으로 자동 배포
Docker Space 배포도 같은 스크립트에 남김(--sdk docker)유료 플랜을 쓰게 되면 Streamlit 화면을 그대로 올릴 수 있음. API 키가 없으면 화면이 실시간 질문이 꺼져 있다고 알리고, 남은 질문 수 표시를 숨기고, 소스 저장소 링크를 보여 줌정적 페이지만 지원

확인한 것

읽기 전용 캐시로 화면을 띄워 예시 질문을 실제로 돌려 봤습니다. 새로 든 비용은 없습니다. 예시 질문 3개 모두 답변이 나왔고, 문장 6개, 6개, 5개가 모두 지지로 표시됐습니다. 문장마다 초록 구절이 붙고 출처 카드가 나옵니다. MSI-H와 PD-1 억제제 질문의 답변을 처음 만들 때의 비용은 $0.25였습니다. 변형 D의 검증 단계가 실제 답변에서 끝까지 도는 것도 이때 처음 확인했습니다.

정적 페이지는 로컬에서 띄워 예시 3개가 그려지고 콘솔 오류가 없는 것을 확인한 뒤 올렸습니다. 공개 주소에서 페이지와 examples.json이 응답하는 것도 확인했습니다.

기술 결정

결정이유버린 대안
MCP SDK 2.x의 MCPServer 사용현재 SDK 기준. 1.x의 FastMCP가 2.x에서 이름이 바뀌었으므로 처음부터 2.x로 작성mcp<2 고정
검색 엔진은 PubMed API 자체3,700만 건을 인덱싱하지 않고 바로 쓸 수 있고, 관련도 정렬 품질이 충분. 대신 검색어 재작성을 에이전트의 일로 둠자체 벡터DB 인덱싱
SQLite 응답 캐시 + readonly 모드NCBI 속도 제한 준수, 평가 재현성, CI에서 네트워크 없이 재생매번 실시간 호출
업스트림 오류를 짧은 도구 오류로 변환에이전트가 스택 트레이스 대신 "재시도하거나 다른 도구 사용"을 읽고 행동예외 그대로 전달
테스트 픽스처는 가상 데이터인용 진실성을 다루는 프로젝트에서 실제처럼 보이는 가짜 인용을 만들지 않음실제 응답 녹화본 커밋
평가 하네스 직접 작성지표 정의를 면접에서 직접 설명할 수 있어야 함. RAGAS는 참고 지표로만RAGAS 단독
모든 변형에 같은 모델 · effort · 출력 스키마변형 간 차이를 모델이 아니라 설계(검색, 에이전트, 검증)에서 온 것으로 해석하기 위해변형마다 최적 모델
LLM 응답도 SQLite에 캐시재채점과 CI 재생에 API 비용이 들지 않음. 새 표본이 필요하면 캐시를 끄고 실행매번 새로 호출
Claude 호출에 fallbacks: "default"안전 분류기가 생의학 질문을 오탐해 거절하면 문항이 통째로 빠짐. 대신 응답한 모델을 기록해 결과에 표시거절을 오답으로 처리
PubMedQA는 PMID · 질문 · 라벨만 저장원본 JSON의 초록(CONTEXTS)과 결론(LONG_ANSWER)은 저장하지 않음. 고정 시드로 재추출 가능원본 파일 커밋

범위 밖

  • 자체 벡터DB 대규모 인덱싱, 모델 파인튜닝
  • 전문(full text) 대량 저장·재배포. 초록과 오픈액세스 본문만 실시간 조회
  • 임상 의사결정 지원. Intended use는 "연구 문헌 탐색 보조"
