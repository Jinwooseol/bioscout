설계

"에이전트를 만들었다"가 아니라 "평가로 인용 정확도를 얼마나 올렸다"는 숫자를 남기는 것이 목표입니다. 그래서 평가셋과 baseline을 먼저 만들고, 기능은 하루에 하나씩 더하며 숫자로 효과를 확인합니다.

성공 기준

기준목표
평가 규모PubMedQA 100문항 + 도메인 25문항, 변형 4개(A–D) 비교표
가짜 PMID 비율 (변형 D)0%
Citation precision (변형 D)0.90 이상, 단순 RAG(B) 대비 개선 폭 제시

공개 결과물GitHub 레포, 공개 데모 URL, 홈페이지 케이스 스터디, LinkedIn 글

아키텍처

도구(MCP 서버), 추론(에이전트), 평가(하네스)를 분리해 각각 따로 교체하고 테스트합니다. 데모와 평가 하네스는 같은 에이전트를 부르므로, 데모에서 보이는 품질이 곧 평가 수치입니다.

데이터 계약

에이전트는 자유 텍스트가 아니라 아래 구조로 답합니다. 문장 단위로 인용과 판정이 붙어 있어야 데모는 배지를 그리고, 평가 하네스는 지표를 계산할 수 있습니다. 평가 하네스가 먼저 필요해 src/bioscout/answer.py의 Pydantic 모델로 먼저 고정했습니다.

{
  "question": "MSI-H 대장암에서 PD-1 억제제 반응률은 MSS보다 높은가?",
  "decision": "yes",                   // yes | no | maybe | not_applicable (PubMedQA 채점용)
  "sentences": [
    {
      "text": "MSI-H 종양군의 객관적 반응률이 MSS군보다 높게 보고되었다.",
      "citations": ["10000002"],
      "verdict": "supported",          // supported | partial | unsupported
      "evidence": "초록에서 판정 근거가 된 문장"
    }
  ],
  "dropped": [ { "text": "...", "citations": ["10000003"], "reason": "unsupported" } ],  // not_backed | unsupported
  "searches": [ { "query": "\"microsatellite instability\"[MeSH] AND ...", "pmids": ["..."] } ],
  "context_pmids": ["10000002"],       // 답변 단계에 초록을 준 PMID
  "usage": { "usd": 0.0, "latency_ms": 0, "tool_calls": 0, "model": "claude-opus-5-5" }
}

평가 설계

평가가 이 프로젝트의 본체입니다. 같은 평가셋, 같은 지표로 네 변형을 비교하고 그 결과표가 README와 LinkedIn 글의 헤드라인이 됩니다.

평가셋

셋규모구성재는 것
PubMedQA 서브셋100문항전문가 라벨 셋(PQA-L)에서 무작위 추출, 문항마다 원 논문 PMID 존재정답률, 원 논문 검색 성공률
도메인 셋25문항MSI · dPCR · liquid biopsy 질문 직접 작성, 문항마다 꼭 인용할 PMID와 핵심 포인트 2–4개핵심 포인트 커버리지, must-cite recall
판정 보정셋60쌍에이전트 출력의 (문장, 인용 초록) 쌍을 직접 라벨링LLM judge와 사람 판정의 일치도
범위 밖 질문10문항개인 치료 결정 요청 등연구 탐색 범위로 안내하는지

지표

지표정의판정 방식
가짜 PMID 비율인용한 PMID 중 PubMed에 없는 비율check_pmids, 결정적
Citation precision인용 중 해당 문장을 실제로 지지하는 비율LLM judge, 보정셋으로 검증
Citation coverage사실 진술 문장 중 지지 인용이 1개 이상인 비율LLM judge
정답률 · 키포인트 커버리지PubMedQA 라벨 일치, 도메인 셋 핵심 포인트 포함 비율규칙 + LLM judge
Retrieval recall@10정답 PMID가 검색 상위 10건에 들어간 비율결정적
비용 · 지연질의당 USD, p50/p95 지연, 도구 호출 수. 집계 방식실행 기록 집계

비교 변형

변형구성보여주는 것
A. LLM 단독도구 없이 답변 + PMID 인용 요청인용 환각이 실제로 얼마나 일어나는가
B. 단순 RAG질문 그대로 PubMed 상위 10건 초록 → 답변일반적인 RAG의 한계
C. 에이전트질문 분해, MeSH 검색어, 초록 선별, 재검색 1회. 상세 설계에이전트 설계의 효과
D. 에이전트 + 검증C + 인용 판정, 인용 정리, 고쳐 쓰기 1회, 삭제. 상세 설계검증 루프의 효과와 그 비용

PubMedQA 질문은 논문 제목에서 만들어져 검색 성공률이 낙관적으로 나오고, 모델이 학습 중 봤을 가능성도 있습니다. 그래서 직접 만든 도메인 셋 결과를 항상 함께 제시합니다.

평가 하네스

평가 하네스는 "문항 × 변형"마다 답변을 하나 받아, 사람 손을 거치지 않는 결정적 지표부터 채점합니다. 판정이 필요한 지표(citation precision, coverage)는 judge가 같은 레코드 위에 더합니다. 그래서 레코드는 나중에 다시 실행하지 않고 재채점할 수 있게 원자료를 모두 남깁니다.

리서치 에이전트 구현됨

변형 C는 B와 같은 답변 단계에 "무엇을 읽을지 고르는 일"만 더합니다. 질문을 개념으로 나눠 검색어를 쓰고, 찾은 초록을 읽어 근거가 되는 논문만 고르고, 부족하면 한 번 더 찾습니다. 답변 단계의 시스템 프롬프트, 출력 스키마, 초록 수 상한(10건)은 B와 같습니다. 그래서 B와 C의 차이는 "어떤 초록을 읽었나"에서만 나옵니다.

노드

노드하는 일입력 → 출력호출상한
plan질문을 개념(대상, 개입·노출, 결과, 비교)으로 나누고 개념마다 MeSH와 [tiab] 동의어로 검색어를 씀. 반대 근거를 찾을 넓은 검색어도 하나 넣음질문 → 하위 질문과 검색어LLM 1회검색어 4개

설계 결정

결정이유버린 대안
답변 단계는 B와 같은 시스템 프롬프트, 스키마, 초록 상한 10건B 대비 개선이 검색·선별에서 왔다고 말할 수 있음. 공유 프롬프트는 src/bioscout/prompts.py로 옮겨 두 변형이 같은 상수를 씀에이전트 전용 답변 프롬프트
정해진 그래프 + 조건부 재검색 1회질의당 LLM 호출이 3–4회로 정해져 비용 상한이 분명함. 단계마다 JSON 호출 하나라 응답 캐시로 재생되고, 가짜 LLM으로 단계별 테스트 가능모델이 도구를 자유롭게 부르는 tool-use 루프. 호출 수가 문항마다 달라 비용과 재현성이 흔들림
1라운드에 질문 그대로 검색도 실행하고, 그 결과를 후보 맨 앞에 둠첫 실행에서 넓은 MeSH 검색이 PubMedQA 원 논문을 상위 10건에서 놓쳐, C가 B보다 덜 찾았음(원 논문이 답변 초록에 든 비율 40% vs 90%). 이렇게 하면 C가 고를 후보에 B가 답변에 쓰는 초록 10건이 늘 들어감계획 노드에 논문 제목 같은 검색어를 쓰게 하기. PubMedQA에만 맞춘 요령이 됨
선별 노드의 새 검색어도 계획과 같은 형식 규칙(QUERY_SYNTAX)을 따름첫 실행에서 선별 노드가 쓴 키워드 나열은 PubMed가 단어마다 AND로 묶어 0–3건만 돌려준 경우가 많았음형식 자유
LangGraph StateGraph검증 루프(조건 분기와 순환)를 노드로 붙이고, Langfuse가 노드 단위로 트레이스함순수 async 함수 체인
선별은 제목이 아니라 초록 전체를 읽음근거는 초록의 결과·결론에 있음. 후보 25건이면 입력 약 9K 토큰제목만 보고 고르기
ClinicalTrials.gov와 본문은 변형 C에서 쓰지 않음인용 단위가 PMID이고 judge는 초록으로 판정함. 시험 등록 정보나 본문에만 있는 근거는 채점도 검증도 할 수 없음. "범위를 줄여야 할 때" 1번과도 같음도구 5개 모두 사용
선별이 후보에 없는 PMID를 고르면 버림답변 단계에는 실제로 가져온 초록만 들어감. 답변의 인용 검사는 하지 않음(변형 D의 일)답변 후 인용 필터링
그래프 설정값도 prompt_sha에 포함검색어 수나 라운드 수만 바꾼 실행도 다른 실행으로 기록됨. A·B의 해시는 바뀌지 않게 유지프롬프트만 해시

인용 판정 judge 구현됨

judge는 답변의 문장 하나와 그 문장이 인용한 초록들을 받아, 초록이 문장을 뒷받침하는지 판정합니다. 평가에서는 이 판정으로 citation precision과 coverage를 계산합니다. 변형 D에서는 같은 judge가 답변을 보여 주기 전에 문장을 걸러 냅니다.

판정 단위와 기준

대상판정기준
인용 하나
초록 하나만 보고		supported초록이 문장의 사실 주장 중 적어도 하나를 분명히 말함. 효과의 방향이 같고, 문장이 대상, 조건, 수치를 말했다면 그것도 같음
partial같은 결과를 다루지만 느슨하게만 뒷받침함. 더 약하거나 좁은 결과, 다른 대상이나 결과 지표, 맞지 않는 수치
unsupported문장의 어떤 주장도 뒷받침하지 않거나 반대임. PubMed에 없는 PMID와 초록이 없는 논문도 여기에 넣음
문장
인용한 초록 전체를 보고		supported문장의 모든 사실 주장이 적어도 한 초록에 분명히 있음
partial일부 주장만 뒷받침되거나, 느슨하게만 뒷받침됨
unsupported뒷받침되는 주장이 없음. 인용이 없는 문장도 여기에 넣음

judge는 주어진 초록만 보고 판정합니다. 사실인 문장이라도 초록에 없으면 지지가 아닙니다. 판정마다 근거가 된 초록 구절을 40단어 이내로 그대로 옮기게 하고, 그 구절이 실제로 초록에 있는지 코드로 대조합니다. judge가 구절 여러 개를 "..."로 이어 붙인 경우에는 조각마다 초록에 있는지 봅니다.

흐름

  1. 답변이 인용한 PMID의 초록을 PubMed에서 가져옵니다(캐시).
  2. PubMed에 없는 PMID와 초록이 없는 논문은 LLM을 부르지 않고 unsupported로 둡니다.
  3. 판정할 초록이 하나라도 있으면 문장마다 LLM을 한 번 부릅니다. 질문, 문장, 인용한 초록들을 주고 인용별 판정과 근거 구절, 문장 판정, 뒷받침되지 않은 부분을 받습니다.
  4. 일관성 규칙을 코드로 적용합니다. 문장 판정은 가장 좋은 인용 판정보다 높을 수 없고, supported 인용이 있으면 문장은 partial 이상입니다. judge가 빠뜨린 PMID는 unsupported로 두고, 주지 않은 PMID에 대한 판정은 버립니다.
  5. 결과를 evals/runs/<run_id>/judgments.jsonl에 문장 단위로 저장합니다. 답변 레코드는 바꾸지 않습니다.

설계 결정

결정이유버린 대안
문장마다 한 번 호출하고, 그 문장이 인용한 초록을 모두 줌"A이고 B이다 [1][2]"처럼 초록 둘이 나눠 뒷받침하는 문장을 문장 단위로 판정할 수 있음. 인용별 판정도 같은 호출에서 받음(문장, 초록) 쌍마다 호출. 문장 전체가 뒷받침되는지 알 수 없음
판정은 3단계데모의 배지와 같음. "주제는 맞지만 주장이 다른" 인용을 무관한 인용과 구별함지지 / 비지지 2단계
Precision은 supported만 셈성공 기준(0.90)이 느슨해지지 않음. partial은 따로 보고partial을 0.5로 계산
Coverage의 분모는 답변의 전체 문장인용 없는 사실 문장은 확인할 수 없으니 뒷받침되지 않은 것으로 봄. "초록이 이 질문에 답하지 않는다" 같은 문장도 분모에 들어가는 한계가 있음사실 문장만 골라 분모로 쓰기. 프롬프트가 하나 더 필요해, 보정에서 문제가 되면 추가
근거 구절을 그대로 옮기게 하고 코드로 대조judge가 초록에 없는 근거를 만들어 내는지 싸게 확인함근거를 요약으로 받기
답변과 같은 모델, 같은 effort설정을 하나로 유지함. judge는 어느 변형의 답변인지 모름. 자기 답변에 후한지는 사람 라벨과의 일치도로 확인다른 모델을 judge로 쓰기
판정을 레코드와 다른 파일에 저장judge 프롬프트를 바꿔도 답변을 다시 만들지 않고 재판정함. 판정마다 judge 프롬프트 해시를 남김레코드에 덮어쓰기
일부만 판정한 그룹은 리포트에 judge 지표를 넣지 않음몇 문항만 시험 판정한 수치가 전체 실행의 수치 옆에 놓이면 전체 결과로 읽힘. 판정한 부분의 수치는 judge 명령이 화면에 따로 출력판정된 문장만으로 계산해 리포트에 넣기
초록과 근거 구절은 Git에 넣지 않음판정 파일은 Git에서 제외한 evals/runs/에만 둠. 리포트에는 집계만 들어감판정 파일 커밋

보정: judge를 사람 판정과 비교 도구 구현됨 라벨링 대기

judge 수치를 믿으려면 사람 판정과 맞는지 봐야 합니다. 판정 결과에서 (문장, 인용 초록) 60쌍을 뽑아 직접 라벨링하고, 인용 판정의 Cohen's kappa가 0.7 이상인지 확인합니다. 낮으면 어긋난 쌍을 읽고 프롬프트를 고친 뒤 다시 잽니다.

단계하는 일이유
추출judge가 LLM으로 판정한 인용을 판정별(supported, partial, unsupported)로 나누고, 판정마다 같은 수를 뽑음. 한 판정이 모자라면 남는 몫을 다른 판정에 넘김. 각 판정 안에서는 변형 A, B, C에서 번갈아 뽑음전체 인용의 86%가 supported라 무작위로 뽑으면 60쌍 중 unsupported가 1쌍도 안 나옴. 그러면 judge가 틀린 인용을 잡는지는 확인할 수 없음
라벨링 파일쌍마다 질문, 문장, 초록 하나를 적은 Markdown 파일을 evals/review/에 만듦. 순서를 섞고, judge 판정과 변형은 적지 않음. 어느 쌍인지는 옆의 .pairs.json에만 남김judge 판정을 보고 라벨을 달면 일치도가 부풀려짐. 초록이 들어 있어 Git에는 넣지 않음
라벨쌍마다 label: 뒤에 s, p, u 중 하나를 적음. 기준은 judge 프롬프트와 같은 인용 판정 기준사람과 judge가 같은 질문에 답해야 비교가 됨
채점일치율, 3단계 Cohen's kappa, supported 대 나머지의 kappa, 혼동 행렬, 어긋난 쌍 목록을 냄. 모두 라벨링하면 수치만 evals/reports/<run_id>.calibration.json에 저장하고 리포트에 한 줄을 더함precision은 supported만 세므로, supported와 나머지의 경계가 맞는지를 따로 봄

판정별로 같은 수를 뽑은 표본이라, 여기서 나온 일치율은 전체 인용의 일치율과 다릅니다. 이 표본은 judge가 세 판정을 사람처럼 가르는지를 보려는 것입니다. 같은 실행과 같은 시드로는 늘 같은 60쌍이 나옵니다. 라벨이 적힌 파일은 덮어쓰지 않습니다.

시험 판정과 비용

전체 실행의 답변 19개(인용 문장 66개)에 judge를 먼저 돌렸습니다. A가 번호를 4만큼 틀리게 적은 인용(10430922)은 unsupported로 판정됐습니다. judge가 옮긴 근거 구절 102개는 모두 초록에서 확인됐습니다. 비용은 문장당 약 $0.013(입력 2.0K, 출력 0.2K 토큰)입니다. 판정도 캐시되므로 다시 돌릴 때는 비용이 들지 않습니다.

verify아직 판정이 없는 문장을 인용한 초록과 맞대어 judge로 판정함. 판정에 따라 인용을 정리함: supported 인용만 남기고, 없으면 partial 인용을 남김. 에이전트가 가져온 적 없는 PMID는 초록이 없으므로 근거 없음으로 봄문장당 LLM 1회, 동시에
revise완전히 뒷받침되지 않은 문장(partial, unsupported, 인용 없는 문장)을 모아, 답변에 쓴 초록 안에서 고쳐 쓰게 함. 뒷받침되지 않는 부분을 빼거나 좁히고, 대상과 수치를 초록에 맞춤. 남길 내용이 없으면 빈 문장을 돌려주고 그 문장은 삭제됨답변당 LLM 1회, 필요할 때만
verify (다시)고쳐 쓴 문장만 다시 판정함고친 문장당 LLM 1회
finish근거 없음으로 남은 문장을 삭제하고 dropped에 이유와 함께 기록함. 부분 지지 문장은 판정을 단 채 남김없음

설계 결정

결정이유버린 대안
C와 같은 그래프에 검증 노드만 더함앞부분이 C와 같은 요청을 보내 캐시된 응답을 재생함. D와 C의 차이를 검증 단계의 효과로 읽을 수 있음. C의 프롬프트 해시는 바뀌지 않게 테스트로 고정D 전용 파이프라인
인용 정리: 지지한 인용만 남김문장을 뒷받침하지 않는 인용이 빠져 precision이 오름. 문장 판정이 supported이면 지지한 인용만으로도 그 판정이 유지됨인용을 그대로 두고 문장만 걸러 내기
부족한 문장은 다시 검색하지 않고, 답변에 쓴 초록 안에서 한 번 고쳐 씀전체 판정에서 C의 문장 632개 중 근거 없음은 0개였고, 부분 지지 40개는 대부분 초록에 없는 세부(수치, 대상)를 덧붙인 경우였음. 주장을 초록에 맞게 좁히면 해결됨. 재검색은 문장마다 LLM 호출 2회와 검색이 더 들고, 새 초록을 다시 선별해야 함문장마다 재검색. D를 평가한 뒤에도 근거 없는 문장이 문제로 남으면 추가
고쳐 쓰기는 한 번, 답변당 호출 한 번비용 상한이 분명함. 한 번 고쳐도 부분 지지면 표시하고 넘어감지지가 될 때까지 반복
부분 지지 문장은 지우지 않고 표시주제가 맞는 근거가 있고, 읽는 사람이 판단할 수 있음. 지우면 답변이 빈약해짐부분 지지도 삭제
확인하지 못한 문장은 지우지 않음judge 호출이 거절된 것은 문장의 잘못이 아님. 판정 없음으로 남겨 화면에서 구별함확인 못 한 문장 삭제
삭제한 문장을 이유와 함께 기록무엇이 빠졌는지 추적할 수 있고, 평가에서 답변당 삭제 문장 수를 집계함조용히 삭제

D의 수치를 읽는 법

D는 judge로 거른 답변입니다. 그 답변을 같은 judge로 다시 채점하면 precision은 구조적으로 높게 나옵니다. 그래서 D의 citation precision은 "judge가 supported라고 한 인용을 사람도 그렇게 보는 비율"만큼만 믿을 수 있고, 이 비율은 보정 표본에서 나옵니다. D의 결과는 보정 결과, 답변당 삭제한 문장 수, coverage, 비용과 함께 봅니다.

비용 추정과 테스트

질의당 비용은 C에 문장 판정(문장당 약 $0.013, 답변당 5–6문장)과 수정 호출(필요한 답변에만 약 $0.03)이 더해져 약 $0.22–0.25로 예상합니다. 이미 판정한 실행과 같은 문항으로 D를 돌리면 C 단계와 고치지 않은 문장의 판정이 캐시에서 재생되므로, 새로 드는 비용은 수정 호출과 고친 문장의 재판정뿐입니다. judge 프롬프트가 바뀌면 D의 답변도 달라지므로, D 실행은 judge 보정 뒤에 합니다.

테스트는 가짜 LLM으로 경로마다 확인합니다. 인용 정리, 고쳐 쓴 뒤 재판정, 한 번 뒤에는 더 고치지 않음, 두 가지 삭제, 인용 없는 문장, 거절된 호출입니다.
