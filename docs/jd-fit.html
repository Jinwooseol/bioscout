채용 요건 대조

LLM · AI 에이전트 엔지니어 공고가 요구하는 기술을 이 프로젝트에서 한 일과 나란히 놓았습니다. 한 것은 근거가 되는 파일과 수치를 적고, 하지 않은 것은 하지 않았다고 적습니다.

기준으로 삼은 요건

2026년 공고와 직무 안내를 검색해 여러 곳에 반복해서 나오는 항목을 모았습니다. 공고 몇 개를 본 것이라 모든 회사의 요건은 아닙니다.

  • LLM API(OpenAI, Anthropic)를 능숙하게 다루고, LangGraph나 DSPy를 써 봤고, MCP 서버를 구성할 줄 알 것 (Dice, LLM Engineer)
  • LangChain, LlamaIndex 같은 프레임워크와 임베딩, RAG 시스템 경험 (UPS, Senior AI Engineer)
  • RAG, 에이전트, 도구 사용, 파인튜닝이 들어간 LLM 애플리케이션을 운영 수준으로 만든 경험 (DRIVENETS, Senior AI Engineer)
  • 에이전트 엔지니어는 프롬프트, RAG에 더해 오케스트레이션, 도구, 평가를 다룸 (Techademy 직무 안내)
  • 국내 공고(원티드, 리멤버 검색 결과): LangChain이나 LangGraph로 에이전트 또는 RAG 시스템을 만든 경험(개인 프로젝트 포함), 트레이싱 · 평가 · 개선을 반복해 본 경험(LangSmith, Langfuse, 자체 평가셋), 평가 · 모니터링 · 가드레일 설계, 벡터 검색과 임베딩, 비동기 큐와 Docker · Kubernetes

대조표

요건이 프로젝트에서 한 것근거판단
LLM API, 구조화 출력, 프롬프트 관리Claude API를 JSON 스키마 출력으로 호출. 변형마다 프롬프트 해시를 내고 테스트에 고정. 모델이 거절하면 기본 모델로 넘기고 기록src/bioscout/llm.py, prompts.py, tests/test_agent.py충분
에이전트 오케스트레이션 (LangGraph)계획, 검색, 선별, 인용 답변, 검증, 고쳐 쓰기를 상태 그래프로 실행. 근거가 부족하면 한 라운드 더 검색. 단계마다 비용과 시간을 기록src/bioscout/agent/graph.py, 설계충분 에이전트 하나의 그래프이고 멀티 에이전트는 아님
MCPPubMed, Europe PMC, ClinicalTrials.gov를 도구 5개로 내는 MCP 서버. Claude Code와 Claude Desktop에 연결해 사용. 에이전트도 같은 도구를 MCP 클라이언트 세션으로 부를 수 있음src/bioscout/mcp_server.py, tools.py. 예시 질문 3개가 직접 호출과 MCP 호출에서 같은 답변으로 재생됨충분
RAG, 검색MeSH 검색어를 다시 쓰는 PubMed 검색에 질문 그대로의 검색을 더하고, LLM이 초록을 읽어 10편을 고름. 단순 RAG를 baseline으로 두고 비교. 초록을 임베딩 유사도로 고르는 변형(E)도 만들어 LLM 선별과 비교원 논문이 답변에 쓰인 비율: 단순 RAG 85%, 에이전트 91%. 임베딩 선별 변형은 에이전트 비용의 37%로 인용 정확도 85.5%(에이전트 86.1%), 근거가 확인된 문장 91.7%(93.4%), 정답률 73%(76%). 임베딩 선별충분 벡터 DB는 쓰지 않음(질문당 후보 25편)
평가115문항, 같은 모델로 변형 4개, 결정적 지표, LLM judge, 사람 라벨과 비교하는 보정 도구(Cohen's kappa), 실패 분류, CI 평가 게이트src/bioscout/evals/, evals/reports/. judge가 인용 문장 1,151개를 판정충분 보정 라벨링은 진행 중
트레이싱, 관측 (Langfuse, LangSmith)답변마다 단계별 비용, 토큰, 호출 수, 지연을 기록하고 리포트에 표로 냄. 답변 하나를 trace 하나로, 단계와 모델 호출과 PubMed 호출을 OpenTelemetry span으로 내보내 Langfuse로 보냄비용 · 지연 집계, 트레이싱. 에이전트 비용의 66%가 선별 단계충분 실제 Langfuse 화면에서는 아직 확인하지 않음
가드레일, 신뢰성인용한 PMID가 실제로 있는지 확인. 초록을 받아 쓴 답변은 그 초록만 인용하도록 제한. 문장마다 인용 초록이 뒷받침하는지 판정하고, 부족하면 한 번 고쳐 쓰고, 그래도 근거가 없으면 삭제. 의료기기가 아니라는 안내src/bioscout/verifier/. 세 변형의 인용 1,681건 중 가짜 PMID 0건충분 초록에 섞인 지시문(프롬프트 인젝션)은 따로 시험하지 않음

받을 만한 질문과 답할 근거

질문근거
에이전트가 단순 RAG보다 6배 비싼데 정답률은 같다. 왜 쓰나?근거가 확인된 문장이 82%에서 93%로 늘고, 근거 있는 문장이 하나도 없는 답변이 24개에서 0개로 줄어듦. 도메인 질문은 단순 검색으로 15개 중 13개가 0건. 정답률이 같은 이유는 실패 분류에 있음: 에이전트의 오답 24건 중 19건은 라벨이 yes나 no인데 maybe로 답한 경우
가짜 PMID가 0%면 인용 문제는 없는 것 아닌가?존재 확인만으로는 변형이 구분되지 않음. LLM 단독은 가짜 PMID가 없지만 인용의 절반이 문장을 분명히 뒷받침하지 않고, 그중 일부는 주제가 다른 실제 논문
LLM judge의 판정을 어떻게 믿나?judge가 근거로 옮긴 구절이 초록에 실제로 있는지 코드로 확인함. 판정 기준별로 같은 수의 쌍을 뽑아 저자가 가린 채 라벨링하고 Cohen's kappa를 냄(목표 0.7). 이 비교가 끝나기 전의 수치는 잠정이라고 표시
에이전트를 바꿨을 때 품질이 떨어지지 않았는지 어떻게 아나?CI 평가 게이트. 프롬프트나 설정이 바뀌면 평가를 다시 돌리기 전까지 CI가 실패하고, 새 수치가 한도 넘게 떨어져도 실패
공개 서비스로 열면 비용을 어떻게 막나?질문 수 한도. 모든 호출자가 함께 쓰는 하루 20개, 전체 200개 한도를 SQLite 파일에 두어 다시 시작해도 남음. 검증을 켠 질문 하나가 약 $0.25이므로 하루 약 $5, 전체 약 $50이 상한. 답변은 동시에 2개까지, 하나에 300초까지. 호출자 한 명은 하루 5개까지라 한 사람이 하루치를 다 쓰지 못함. 키에는 공급자 쪽 지출 한도를 따로 걸어, 코드가 틀려도 상한이 지켜지게 함
MCP 서버는 에이전트와 어떤 관계인가?같은 PubMed 클라이언트와 캐시를 두 경로로 씀. 기본은 프로세스 안에서 직접 호출이고, BIOSCOUT_TOOLS=mcp면 MCP 클라이언트 세션으로 도구를 호출. 두 경로의 답변이 같은 것을 테스트와 재생으로 확인
BioScout는 문헌 탐색을 돕는 도구이며, 개별 환자의 진단이나 치료 결정에 쓰지 않습니다.
